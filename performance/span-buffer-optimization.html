Span Buffer Optimization

Published on Monday, October 26, 2026

The span buffer is an extremely high-throughput, and memory intensive, span-buffering process at Sentry. While on a visit to the San Francisco office I had the opportunity to go to dinner (and a bar or two or three...) with a few friends from some other teams within the company. Despite their introverted reputation, software engineers love to talk, and they especially love to complain. On this trip the span buffer was the unfortunate recipient of their ire. This is what first alerted me to the span buffer's less-than-satisfactory reputation. I had always known it existed but I wasn't aware how much mental capacity its problems seemed to be consuming. Most of the engineers wanted to improve the situation but none could find the time.

This was somewhat serendipitous as I was in between projects and had the freedom to decide what I wanted to work on. I thought I might throw myself at the problem and see what improvements could be made. There wouldn't be enough time or buy-in to perform large architectural changes, but small incremental improvements could be stomached and, with enough of them, I could perhaps push this thing out of the redline and into a more palatable organge or yellow area of the system health monitor.

One of the core components of the program was Redis. Redis was not only our distributed memory store for the terabytes of span data we received but it was also a sort of synchronization engine and program-state store for use in our distributed processing pipeline. Redis therefore was a high-value target. Reducing interactions with Redis would keep our processing pipeline fast and our Redis cluster healthy. A review of the traces stored in Sentry and the metrics in our DataDog dashboard showed Redis was significant part of the time spent processing each span.

Our Redis usage fell into two broad categories. First, were all of the discrete interactions the pipeline would inititate with Redis.These are the normal GET, SET, HSET, ZREM, etc. operations anyone who has used Redis before knows to expect. The second category was a Lua script called "add-buffer.lua". This was executed once by each span and executed many commands to Redis. This made it slow relative to normal Redis commands. This is particularly important because Redis is single-threaded. A slow command can significantly reduce throughput and harm the latency of the other, faster commands. More importantly, though unknown to me at the time, was the cost of the Lua script itself. It allocated memory and performed computations which (obviously) were not free and had the accumulated effect of significantly slowing the command's execution.

The largest single win achieved during the project was made by removing an unncessary request. The pull request ref(span-buffer): Exit early if the add_buffer script was previously loaded removed a call to the "script_exists" Redis operation. If we had a cached script SHA in memory it meant the script had already been loaded by the process. A change to the script while the pipeline process was live was impossible. This was an entirely safe operation to perform. The immediate result of this pull request was a 30% drop in total pipeline processing time.

A second change, this time within the "add-buffer.lua" script, was to batch looped Redis operations by using their bulk equivalents, and to remove duplicate commands by use of a local cache. ref(span-buffer): Cache previous lookups to Redis in a local array and ref(span-buffer): Skip the EXISTS check by using child_ic heuristic did just that. All together the savings from these two operations saved 2.3 million commands per second. Which is a very impressive number to advertise to your manager. However, the total time savings was only a little more than 50% of total script execution time. A large delta but not so large as you might initially think given the context. In the end, I traded some cross-process (de)serialization for some in-process hashing and memory allocation.

A third change which had significant impact was the optimization of the Lua script itself. Memory allocations, string formatting, metrics tracking, function calling, and function result serialization all presented significant performance opportunities. ref(span-buffer): Reduce Lua memory allocation pressure and function call overhead, ref(span-buffer): Sample metrics collection, and ref(span-buffer): Return latency and metrics tables as flattened lists had significant effects on the latency of the "add-buffer.lua" script. The total latency decline constituted greater than 50% of the already improved script execution time. Perhaps as much as 80 microseconds per span was saved, though, the exact figure is now lost to time. The most surprising improvement was the change to the Redis script's output type. A significant amount of time was being spent by the Redis client libary deserializing these binary responses. By returning flattened lists I was able to gain a significant performance uplift. The culprit, once again, was memory allocation, though, the exact details are lost.

Another interesting change happened very early in the pipeline's execution phase. Spans needed to be deserialized and loaded into memory before they could be operated on. Since spans are arbitrary mappings of key, value pairs they can be quite large (up to 10MB), however, we only used a few fields of known size (roughly 500 bytes of data total). The previous implementation used to parse every field and every value before proceeding to ignore them. In the new implementation we would partially deserialize the input and only incur the cost of scanning the unused bytes. ref(span-buffer): Improve performance of span buffer processor with typed msgspec deserializer and ref(span-buffer): Exclusively use msgspec span decoder added a msgspec based JSON parser. The net-result was a 3x performance uplift when comparing like-for-like deserialization, but when comparing the removed overhead from a secondary validation step the improvement was closer to 4x baseline.

With my newly acquired knowledge of the span-buffer I started looking for more hueristics I could apply to skip work. One such change was ref(span-buffer): Optimize fan out to only target possible candidates. Prior to this change, the span-buffer would make requests to Redis which were no-ops but nonetheless incurred a significant performance cost. By using the heuristic outlined in the pull request description I was able to replace an O(n) operation with, essentially, a constant time operation. An enormous 60% decline in script processing time was observed after this change.

There were some other miscellaneous changes. ref(span-buffer): Add pipelined queue deadline lookups and ref(span-buffer): Use bulk project lookup and cache results locally had smaller effects because they were in less frequently accessed portions of the pipeline but nonetheless had a material (though if less than satisfactory) impact.

Conclusion

Thus ends the performance optimization of the span-buffer. My time exhausted the span buffer's total performance improved by nearly 4x. Declinging from a starting point of 200 microseconds per event to a little over 50 microseconds per event. Most of the time is now dominated by compression and span uploads with non-trivial contributions from parsing, queue management, and, of course, the "add-buffer.lua" script. I'm reasonably close to the ceiling of what's achievable with this architecture. Future, more aggressive alterations could be explored, but for now I am finished.
