Agent Sandbox System Performance Review

Published on Monday, August 3, 2026

This article is a performance-focused companion piece to the original "Agent Sandbox Architecture" entry. In this post I will describe what gives this architecture its superior performance characteristics, and how these characteristics influence the architecture's efficiency, stability, and scalability.

The system has three components: the client, the router, and the sandbox. Each has its own responsibilities and performance profile. For the purposes of this blog, I will break each component out into its own section, and discuss its responsibilities, implementation, replacement implementation, and performance characteristics.

This will be a bit more difficult than just discussing a mechanical translation of slow code to fast code. This was a complete rewrite. Many responsibilities were shifted from one component to another and this radically transforms how each component operates. As a result components from the current implementation are not directly comparable to the replacement implementation. I will call out these divergences where relevant.

The Sandbox

The sandbox has two distinct phases of operation: the setup phase and the execution phase. In the setup phase, a git repository is cloned from its origin, a series of build instructions are parsed from the repository, and the customer's software is installed. In the execution phase, internet access is terminated and a Claude Code process is spawned with a prompt passed to it. On completion the agent's response is buffered into memory, serialized to JSON, and sent over the wire to the client.

In the replacement implementation all of these processes are dropped. The setup and execution phase split, cloning of git repositories, installation of customer software, and mandated calling of Claude code are removed. Instead these responsibilties are shifted to the client which has the ability to run arbitrary commands on a sandbox and the ability to disable a sandbox's internet access.

The replacement implementation spawns one process per TCP connection. It links the STDIN buffer to SO_RCVBUFF and the STDOUT and STDERR buffers to SO_SNDBUF. A novel, framed protocol was created to accomodate interleaving between STDOUT and STDERR frames and STDIN and CONTROL frames (here undocumented). The client is responsible for buffering, parsing, decoding, or otherwise handling the sandbox's output.

When discussing the performance variations between the current and replacement sandbox implementation, I will have to take a very narrow focus on local resource usage when executing identical commands and the properties of the network transmission code. The current implementation's lack of capability prevents it from experiencing some of the potential problems it would have faced under an expanded usage pattern.

In the current implementation, output is triply buffered in the sandbox. A process's output is buffered before it is encoded to UTF-8 and serialized into a JSON payload. Each operation allocates a copy. Only after STDOUT and STDERR have been drained can the HTTP response be sent and the connection closed. This triple buffering leads to significantly higher RSS. The sandbox's architecture introduces arbitrarily slow TTFB (time to first byte) and requires clients to hold open idle, arbitrarily long connections. The triple buffering property also meaningfully impacts network performance. Given one gigabyte of in-memory data and a command to send that data to the client, the sandbox is able to respond at roughly 1.8 gigabits per second on my M4 Pro Macbook. This low bandwidth figure is entirely due to the cost of text and JSON encoding and is unrelated to process exeuction latency.

In the replacement implementation, output is not buffered in the sandbox. As data is received from the process it is emitted in frames (max 1 MiB). If the client or the router is unable to accept the frames back-pressure is applied. The process will continue filling the kernel's buffers until its limit is reached and the kernel signals back-pressure to the process. The same is true for STDIN and SO_RCVBUF. Data is recieved in frames. If the process signals back-pressure to the kernel, the kernel will signal back-pressure to the sandbox runtime, and the sandbox runtime will signal back-pressure to the router and on to the client. Data is only ever transmitted if it is consumable by every downstream process. Given a source of /dev/urandom and a sink of /dev/null the system will only ever consume 1MiB of memory (plus some overheads) for each machine in the connection chain. This system of back-pressure communication is suprisingly cost free. Given one gigabyte of in-memory data and a command to send that data to the client, the sandbox is able to respond at a little over 6 gigabits per second on my M4 Pro Macbook. This is nearly the maximum limit of what /dev/urandom (the input source) can produce.

The replacement implementation, at first, might seem like it keeps the sandbox memory stable at the expense of the client. After all, the client will need to buffer and parse the sandbox's process output in its own memory. If the client needs the full response, it is identical (memory wise) to our current system. In cases where you don't need the full response, you can pipe the output of your command into another command which reduces the output's size. For example, to read some JSON from a file, parse it, and return the root level "hello" key does not require loading the entire file into the client's memory. You can execute this command within the sandbox:

cat xyz.json | jq --stream 'select(.[0][0]=="hello") | .[1]'

This is memory efficient for the client because it only ever sees the value of the "hello" key and not the potentially gigabytes of extra JSON data from the original output. It's memory efficient for the sandbox only because we're operating on the stream. A malformed command could consume excess client or sandbox memory. Programmer discretion advised.

The Router

The router has two core responsibilities: proxy client-sandbox interactions and act as an orchestrator for sandbox runtimes. Its current implementation has a number of performance problems which are closely tied to the various correct issues it has. If you're curious about those issues you can find out more in the original article.

In the current implementation when the router receives a request, it records a task in an in-memory array, creates a new worker which will process the request, and returns a task ID to the client. The worker sequentially initiates two long-lived HTTP requests to the sandbox runtime. The first request clones the repository and installs the customer's software. The second request executes the Claude Code process and awaits its output. Each request will update the task state as it transitions through its phases. The client will periodically poll the router for the task information to update its own state.

There are a number of problems with this system. I'm sure you can imagine a few. For the purpose of this blog, I'll focus on the scalability limit. If your task is in-memory then you are forced into a single-server architecture.

A code comment in the current implementation calls out this defect and suggests Redis as a shared state store. This is a fine solution. The system is single-writer so there are no concurrency concerns from this approach. There are other problems this introduces but its outside the scope of this article. If you'd like to learn more you can read my full analysis on the router's implementation.

We can do better than Redis. If we're willing to hold open long-running connections from the router to the sandbox, we can also hold open long-running connections from the client to the router. If the client is persistently connected we solve our server affinity issues. This in turn means we can have more than one router server. Moving task state from the router and to the client solves a whole category of durability issues.

In the replacement implementation, horizontal scalability meant performance was essentially infinite. The router contained no state. Router servers could be added at will. Whatever performance characteristics the current router implementation has the replacement has infinitely (asterisk, asterisk, asterisk) more of it. Even if the current implementation manages its network interactions responsibly, streams outputs, and manages memory and back-pressure responsibly it is still limited by its architectural choices.

Relying on a persistent connection limits your ability to scale down if a router server is claimed by a long-running process. The protocol managed this by emitting "router shutdown" events. These events signalled to the client that the remote's buffers had been drained. The client should terminate its connection to the server and establish a new connection to a different router server. On the sandbox server, STDOUT/ERR buffers can not be drained until a new client connects with a "session resume" event.

In the replacement implementation, I was willing to hold open those long-running connections. If, for some reason, that was not acceptable and we needed to use a polling model, we would drain the sandbox's buffers in bounded chunks and some portion of the task state would need to be stored in the sandbox's memory until the client could retrieve it.

Results

In the replacement implementation network throughput was measured in excess of 6 gigabits per second (a little over triple the baseline). TTFB latency for certain types of tasks went from seconds to microseconds. Memory RSS declined from gigabytes to megabytes for certain types of tasks. Horizontal scaling became a possible demand response. Several memory leaks were fixed (or rather not reintroduced).
