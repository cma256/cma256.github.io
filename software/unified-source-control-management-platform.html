A Unified Source Code Management Platform

Published on Monday, August 3, 2026

Sentry talks to GitHub, GitLab, and eventually Bitbucket from many places at once: the monolith, Seer, notifications, CI, tests. Each of those places wants the same operations. None of them should own tokens, rate limits, or provider quirks.

The Unified Source Code Management Platform is a pip-installable library that makes that constraint the design. Product code never speaks GitHub. It calls typed functions. Those functions run identically whether the process is Sentry, another service, or a unit test. The only thing that changes is who is allowed to touch the network.

One set of functions

Callers write the same code everywhere:

from scm import actions
from scm.types import CreatePullRequestCommentProtocol

if isinstance(scm, CreatePullRequestCommentProtocol):
    actions.create_pull_request_comment(scm, pr_id, body)

Inside Sentry, scm is built with SourceCodeManager.make_client and an API client that already holds installation credentials. In Seer it is make_proxy_client. In tests it is a fake provider. The action, the protocol, and the type checker do not care.

That is the whole product bet. If a feature can call GitHub some other way, access control is optional. If it cannot, every request goes through one door.

Instructions, not RPCs

The usual way to share functions across services is to RPC them. Python's xmlrpc is blocking, does not stream, forbids yield, and does not present the same interface on both sides. We also need to download large repositories. An RPC of domain methods would have grown an endpoint per capability and parsed GitHub JSON on Sentry for work the client already knows how to do.

Providers do not call GitHub. They emit instructions: method, relative path, headers, body, params, stream, credentials set. The injected ApiClient is the only thing that executes them.

In Sentry those instructions go to api.github.com. Outside Sentry they are HMAC-signed and POSTed to Sentry. Sentry attaches tokens, hits the provider, and streams the response back in 64KiB chunks. It does not parse the body. The client provider parses the bytes exactly as it would if it had called GitHub itself.

The library is oblivious to the target. A local Sentry URL instead of GitHub is inconsequential. We receive an HTTP response and apply the same business logic. New capabilities do not need new RPC routes. Writes are never retried. Paths must be relative. Authorization never travels with the client request. Tokens never come back in response headers.

Capabilities you can ask for

Not every provider implements every operation. A single god interface would lie. Each operation is a @runtime_checkable protocol. The Facade base class has none of those methods, so an unguarded call fails typecheck.

At construction we generate a private subclass that copies onto the class body only the methods the provider actually implements. Python 3.12's isinstance inspects the class body, not __getattr__, so isinstance(scm, CreateIssueCommentProtocol) is true only when the method is real. After the guard, MyPy narrows. GitLab can lag GitHub without anyone sprinkling hasattr or # type: ignore.

Adding a capability is implementing it on the provider. The facade picks it up. actions.py takes the protocol, not the manager, so partial fakes typecheck and unsupported operations are uncallable.

One door for access

Credentials, rate limits, kill switches, caching, and observability belong in one place because there is no other HTTP path. The library defines the choke points. Sentry implements policy on the in-process client and on the RPC server's fetchers.

The repository must exist, be active, and belong to the caller's org. Org mismatch looks like a 404 so you cannot probe other orgs. RPC is HMAC over identity on GET and over the body on POST. The proxy is not an open relay: relative paths only, inbound headers limited to accept, content-type, and if-none-match, a 10MB body cap. The client sends installation or application; Sentry picks the token. A referrer tags every metric so quota can be partitioned by feature.

Conditional GET lives in the instruction schema. Application cache, kill switches, and token refresh live in Sentry. If a service used PyGithub directly, none of this would apply. The proxy exists so it cannot.

A library, not a service

Instantiating SourceCodeManager requires an API client. That client decides whether actions hit a provider, Sentry, or a mock. The package has no Sentry SDK dependency. Metrics and error emission are injected. Anyone who agrees to the license can use it.

Product code should be unable to speak GitHub. It speaks protocols. Providers compile that into HTTP. An injected client is the only thing that can attach secrets. In Sentry that client is the integration stack. Outside Sentry it is a streaming HMAC proxy that runs the same client on Sentry's side and returns raw bytes. Tests inject a fake that never leaves process. One set of functions, three runtimes, one security boundary.
