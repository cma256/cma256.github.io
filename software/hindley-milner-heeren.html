Online you will find many tutorials in many languages which teach Hindley-Milner's algorithm W and M. These algorithms walk an abstract syntax tree, collect "constraints", and solve those constraints within a single tree walk. There is, however, an alternative way to implement these algorithms. Its possible to decouple constraint solving from constraint generation by separating the two steps into distinct phases. This was noted by Milner in 1978 and first demonstrated by Mitchell Wand in his paper "A simple algorithm and proof for type inference".

Heeren's contribution was the addition of let-polymorphism in his paper Generalizing Hindley-Milner Type Inference Algorithms. Not let-polymorphism generally, but let-polymorphism in the context of a factored constraint generation and unification algorithm. Let-polymorphism requires a more complete language for modeling constraints. Heeren introduces the concept of implict and explicit constraints in addition to the standard equality constraints. For this reason studying Heeren's paper is more interesting than studying Mitchell Wand's paper.

In fact even Heeren's contributions are out of date as well. Simon Peyton Jones demonstated in his paper "Practical type inference for arbitrary-rank types" that the monomorphic-type restriction on lambda arguments could be lifted -- a major alteration to the algorithm I'll lay out below. Didier Rémy introduced levelled generalization among other innovations. Reading his and Pottier's work The Essence of ML Type Inference in Advanced Topics in Types and Programming Languages would be a significantly better place to start for a production implementation of Hindley Milner type inference.

And still more bad news. There is another, newer system which has significant research attention: bidirectional type checking. Refer to the Bidirectional Typing paper for specifics. I have no personal experience with it, but I can say there is a lot of enthusiasm around the subject. Whether the enthusism translates into more comprehensible concepts and code I can't say.

Given these headwinds, why study Heeren? Heeren is a simple introduction to a particular form of Hindley-Milner. Studying it gives you the opportunity to learn about one of the most legendary ideas in computer science. I don't know where Heeren stands in an education plan of type systems. It may be a worthwhile introduction or a historical curiosity.

That said, if you're here, you probably have some sense of what you're trying to learn and how you want to go about it. I will do my best to present Heeren's algorithm accurately and in its correct context, but reader beware, I am an interested amateur with no academic experience in this field. Reader discretion advised.

Heeren's Implementation

Prerequisites

Before we can start inferring types we need to define a programming language to operate on, or, at the very least, an abstract syntax tree. I'm going to define a recursive enum. Your language may not have enums or your mental model of the problem may be different. Feel free to use whatever data structure you like.

I'll also define a "Type" enum. Again, use whatever type you like to describe this structure. All we need is something we can tag nodes in our AST with.

enum Expr {
    Number(i64),
    Add(Box<Expr>, Box<Expr>)
}

enum Type {
    TNumber
}

Constraint Generation

Generating a constraint implies "this type is equal to that type". The job of a constraint generation algorithm is to recursively walk an AST and assert "T1 == T2". Crucially it does not prove that T1 equals T2. It just asserts it. If the two types are not equal the expression will not "unify" during the constraint solving phase.

Let's define a type signature for our constraint generation function to get started.

fn generate_constraints(expr: &Expr) -> (Type, Vec<(Type, Type)>)

We take an immutable borrow of the expression (we're not going to modify our AST) and we return a type and a vector of doubles known as the constraints. The type we return is the prinicipal type of the expression. The constraints we return constrain that principal type. The principal type is also known as the expression's "most general" type.

The AST I've defined will never generate any constraints. A number is a number. It has no constraints. Soon we'll encounter expressions for which we can not immediately infer a type for. In these cases we'll return a placeholder type which is constrained by the vector of constraints our function returns.

Let's start generating constraints for our AST.

match expr {
    Expr::Number(_) => (Type::TNumber, vec![])
}

The return type of the Number expression is TNumber and it generates no constraints. We hard code literals to their type. There's nothing to infer. There are no constraints to solve. A number's most general type is just a number.

TNumber is a type but its a certain kind of type. Its a monomorphic type. Mono meaning its only one thing. Its not a number and a string. Its just a number. Polymorphic types can have multiple type expressions. The identity function for example has multiple type expressions:

let identity = \a -> a

We expect identity("hello") and identity(12) to pass the type checker and, so, we have our first example of a polymorphic type. Though, we have no way to express it yet. Before we can get there we have a few intermediate steps to get through first.

Continuing on, we'll generate constraints for the addition expression. This is another hard coded type but it will demonstrate the constraint generation process.

Expr::Add(left, right) => {
    let (t1, mut cs1) = generate_constraints(left);
    let (t2, mut cs2) = generate_constraints(right);
    
    let mut constraints: Vec<(Type, Type)> = vec![];
    constraints.append(&mut cs1);
    constraints.append(&mut cs2);
    constraints.push((t1, Type::TNumber));
    constraints.push((t2, Type::TNumber));

    (Type::TNumber, constraints)
}

Expressions are trees. After evaluating both branches of the tree we combine the constraints from both into a single vector and generate a couple more constraints. The addition expression requires its arguments to be number types. It pushes t1 and t2 into the list of constraints and declares their explicit association to the TNumber type. If you passed a string as the first argument to the addition expression, the constraint solver will tell you that a string can not be used in the addition expression.

It is by no means required that the "Add" expression must only accept "number" types, or that its principal type should be a number. It could accept integers, floats, strings, or any other type. I've constrained it to numbers because that's how I want my programming language to operate. If you have different goals then you would express those goals in your constraint generation step.

Solving Constraints

A constraint solver is even easier than a constraint generator (at least for now). We iterate over the constraints and check that they match. If they don't then we raise an error. What could be simpler?

for (c1, c2) in constraints {
    if c1 != c2 {
        panic!("How could you have possibly messed this up?")
    }
}

Later I will produce a constraint solver which has quadratic-complexity and is moderately more complex than this. You can do much better than quadratic complexity and you can solve constraints in a much better way than I will adopt. The goal of this article is understanding. The quadratic, left-biased solver is the most straight-forward way to produce this thing, so that's what I've done.

If you're following along you should be able to run the program. Create an expression, generate the constraints, and pass those constraints to the solver. If your program panics then you know your expression is not a valid type. If no output was returned then you know there was no type error.

We still don't know the prinicipal type of the program. I've not demonstrated how to get that information out of it yet. But since there's only one valid type in our system so far I'm sure you can guess what the principal type is!

If Expressions

Let's return to constraint generation for now. We'll generate quite a few more constraints for quite a few more expression types. Constraint generation will be something we return to frequently in this article.

If-expressions contain three subexpressions. The "condition" expression, the "then" expression, and the "else" expression. Alternatively referred to as "consequence" and "alternative".

If(Box<Expr>, Box<Expr>, Box<Expr>)

The if expression has two rules in our language. First, the "then" and "else" expressions must have the same type. Second, the "condition" expression must be a boolean type.

Let's add a new boolean type to our Type enumeration.

enum Type {
    TNumber,
    TBoolean
}

Next we'll generate constraints for each of the three subexpressions, merge their constraints, apply some of our own constraints, and return a type.

Expr::If((cond, then, els_)) => {
    let t = tygen.fresh();

    let (tcond, mut c1) = generate_constraints(cond);
    let (tthen, mut c2) = generate_constraints(then);
    let (telse, mut c3) = generate_constraints(els_);

    let mut constraints: Vec<(Type, Type)> = vec![];
    constraints.append(&mut c1);
    constraints.append(&mut c2);
    constraints.append(&mut c3);

    constraints.push((Type::TBoolean, tcond));
    constraints.push((t.clone(), tthen));
    constraints.push((t.clone(), telse));

    (t, constraints)
}

Something weird happened. There's this thing called tygen and its littering its fresh() output everywhere! We've generated a fresh type variable. It's just a number. If this is the first time we've generated a type variable its value is 0. Subsequent generations will increment this value. Some programming languages represent this as 'a, 'b, 'c and so on, but this is just a visual representation. Numbers are trivially compared and generated. They're much nicer to work with so that's what we use.

The process of generating constraints for if expressions mostly mirrors addition. Where it differs is in the generation of a fresh type variable. I can not express this strongly enough, fresh type variables are meaningless placeholders. They do nothing except occupy space until we solve them. It's an ID for a row in a database or an index in an array or a pointer to memory. The values of these things are immaterial. They're only important in so far as it allows us to communicate about a type at some location in our abstract syntax tree.

The reason we use a fresh type variable, rather than asserting the "then" and "else" conditions equal each other explicitly, is so we can treat the two branches symmetrically. We don't want to favor one branch of the conditional over the other.

Let's update our implementation to support fresh type variable generation.

fn generate_constraints(expr: &Expr, tygen: &mut TypeGen) -> (Type, Vec<(Type, Type)>)

Add a new Type member "TVariable":

enum Type {
    TNumber,
    TBoolean,
    TVariable(usize)
}

And add a new type "TypeGen":

struct TypeGen(usize);

impl TypeGen {
    fn new() -> Self {
        TypeGen(0)
    }

    fn fresh(&mut self) -> Type {
        self.0 += 1;
        Type::TVariable(self.0)
    }
}

Next we need to solve for the new TVariable constraints. Type variables represent type "holes" in our program. We don't know what the type of this expression should be. The solver's job is to figure that out. We do that by creating a substitution set. If we learn that T0 is equal to TNumber then that substitution is recorded in the map. If we later learn that T0 is equal to TBoolean, we'll lookup T0 in the substitution set, discover that its already equal to TNumber, and raise a unification error. This repeats until you eventually know the type of your program.

fn solve(ty: &Type, constraints: Vec) -> Type {
    let mut subst = HashMap::new();
    for (t1, t2) in constraints {
        unify(&t1, &t2, &mut subst);
    }
    apply_subst(ty, &subst)
}

fn unify(t1: &Type, t2: &Type, subst: &mut HashMap<usize, Type>) {
    if t1 == t2 {
        return;
    }

    match (t1, t2) {
        (Type::TVariable(v), other) | (other, Type::TVariable(v)) => {
            if let Some(bind) = subst.get(&v) {
                unify(&other, &bind.clone(), subst);
            } else {
                subst.insert(*v, other.clone());
            }
        }
        _ => panic!("The types no be equaling"),
    };
}

fn apply_subst(ty: &Type, subst: &HashMap<usize, Type>) -> Type {
    match ty {
        Type::TVariable(i) => subst.get(i).unwrap().clone(),
        _ => ty.clone(),
    }
}

You should know that these constraints we're generating and the solvers we're producing to solve them are incorrect. They're toys to illustrate an idea. In the next section we're going to significantly accelerate to the ending. If I've done an okayish job you should have the gist of what we're doing.

Let Expressions

To support let expressions, we begin by updating the Expr enum with the new expression types. The two expression types are: assignment and reference (let and var).

enum Expr {
    ...,
    Let(String, Box<Expr>, Box<Expr>),
    Var(String),
}

With these new expressions we can write a program that looks like this: let a = 1 in a + 1.

Variables introduce an interesting wrinkle to our type inference algorithm. a has a type which is defined in a location distinct from its usage. When a variable is referenced we need some way to look up its type. The generate_constraints function definition needs to be updated to accept a type environment argument. The environment is a mapping of variable name to type.

Now when we encounter a variable we'll know how to look it up and return its type to the interested caller.

fn generate_constraints(
    expr: &Expr,
    env: &mut HashMap<String, Type>,
    tygen: &mut TypeGen,
) -> (Type, Vec<(Type, Type)>)

Now to finish the section we'll generate constraints for these new expression variants. Variable first.

Expr::Variable(name) => (env.get(name).unwrap().clone(), vec![])

Easy. If you encounter a variable look it up. If an undefined variable is referenced we panic. You're welcome to return a more appropriate error message or detect these errors in an earlier phase of your language's compilation pipeline. For the purposes of this article, however, its out of scope.

Next we'll generate constraints for the Let expression.

Expr::Let(name, value, body) => {
    let (ty1, mut cs1) = generate_constraints(value, env, tygen);
    env.insert(name.clone(), ty1.clone());

    let (ty2, mut cs2) = generate_constraints(body, env, tygen);
    env.remove(name);

    let mut constraints: Vec<(Type, Type)> = vec![];
    constraints.append(&mut cs1);
    constraints.append(&mut cs2);

    (ty2, constraints)
}

Most of the constraint tracking and type generation code are repeats of what we learned already. The new twist is that we store the variable's type in the type environment as the output of the type returned by constraint generation on the value. If a = 1 then a is an Integer type. That association must be maintained in the type environment map.

There's some subtlety here but nothing extreme. Notice when the variable goes out of scope it is removed from the environment. If you're really paying attention (or getting unexplained error messages) you may notice that shadowed variables are overwritten. They are also removed from the environment before the lifetime of the shadowed variable has expired. This is an error waiting to happen if you haven't hit it already. There are a few solutions: disallow shadowing, use a more appropriate data structure which preserves shadowed variables, track them manually, or something else. What you choose to do is up to you. I'm opting for the easy route.

Before we leave this section we need to refactor the constraint generation code we just wrote. We're implementing a type inference algorithm for 'Let-bound polymorphic' programs. Let variables are polymorphic. We don't have a function expression yet so we can get away with treating every variable as monomorphic (as we are now). But if we do that then we're going to compound the amount of work we need to do in the next section. Introducing this distinction earlier than is strictly necessary is useful from an educational and cognitive load-shedding standpoint.

Let's introduce a new enum.

enum Binding {
    Monomorphic(Type),
    Polymorphic(Type, HashSet<usize>),
}

And update our generate_constraints function's type signature to include:

env: &mut HashMap<String, Binding>,
mono_set: &HashSet<usize>,

And finally update our constraint generation to consider monomorphic and polymorphic bindings.

Expr::Let(name, value, body) => {
    let (ty1, mut cs1) = generate_constraints(value, env, mono_set, tygen);
    env.insert(name.clone(), Binding::Polymorphic(ty1, mono_set.clone()));

    let (ty2, mut cs2) = generate_constraints(body, env, mono_set, tygen);
    env.remove(name);

    let mut constraints = vec![];
    constraints.append(&mut cs1);
    constraints.append(&mut cs2);

    (ty2, constraints)
}
Expr::Variable(name) => match env.get(name).expect("Unbound variable").clone() {
    Binding::Monomorphic(ty) => (ty, vec![]),
    Binding::Polymorphic(ty, mono_set) => {
        let poly_ty = tygen.fresh();
        let constraint = Constraint::ImplicitInstance(poly_ty.clone(), ty, mono_set);
        (poly_ty, vec![constraint])
    }
}

"mono_set" is a strange addition. Heeren refers to the "mono_set" as M in his paper. It represents the set of monomorphic type variables the program encountered along that particular branch of the AST -- otherwise referred to as "free". In practice, these are all the type variables which were generated to represent the type of a function parameter. Function parameters are not polymorphic. Their type variables get thrown into the "mono_set" when they're encountered.

"ImplicitInstance" constraints are also a strange new addition. Polymorphism introduces some complexity to constraint solving. The implicit instance constraint gives us the machinery to tame that complexity. I would give you a deeper explanation but at this stage we're not ready. We'll come back to it when we discuss the new constraint solver.

Reality has a suprising amount of detail and so does this type inference algorithm. In the following sections I will coarsely define the type inference algorithm and gradually refine it to its correct state. The algorithm we produce during these intermediate steps will be entirely incorrect, but by doing so I'll be able to gradually reveal deeper, more-subtle properties of the algorithm which might otherwise get washed out by hundreds of lines of prose, or, worse, a few terse, jargon-dense paragraphs.

To make our program compile we're going to add a new Constraint enum and update the generate_constraints signature to its final state:

enum Constraint {
    Equality(Type, Type),
    ExplicitInstance(Type, Type),
    ImplicitInstance(Type, Type, HashSet<usize>),

Functions and their Application

Finally, we introduce the last two expression variants. The function expression and the function application expression. With these variants you can produce interesting programs and interesting type inference algorithms.

enum Expr {
    ...,
    App(Box<Expr>, Box<Expr>),
    Fun(String, Box<Expr>),
}

Since we've introduced a new expression type, our Type enum also needs to change. We'll call it "TArrow". It accepts two arguments. The first argument is the function's argument type and the second argument is the function's body type.

enum Type {
    ...,
    TArrow(Box<Type>, Box<Type>)
}

Now let's generate some constraints.

Expr::Application(function, argument) => {
    let (func_ty, mut func_cs) = generate_constraints(function, env, mono_set, tygen);
    let (arg_ty, mut arg_cs) = generate_constraints(argument, env, mono_set, tygen);

    let ret_ty = tygen.fresh();

    let mut constraints = vec![];
    constraints.append(&mut func_cs);
    constraints.append(&mut arg_cs);
    constraints.push(Constraint::Equality(
        func_ty,
        Type::TArrow(Box::new(arg_ty), Box::new(ret_ty.clone())),
    ));

    (ret_ty, constraints)
}
Expr::Function(param, body) => {
    let param_ty = tygen.fresh();
    env.insert(param.to_string(), Binding::Monomorphic(param_ty.clone()));

    let mut inner_ms = mono_set.clone();
    inner_ms.extend(param_ty.free_vars());

    let (body_ty, body_cs) = generate_constraints(body, env, &inner_ms, tygen);
    env.remove(param);

    let ty = Type::TArrow(Box::new(param_ty), Box::new(body_ty));
    (ty, body_cs)
}

First, the easy stuff. We're generating types and constraints as before. The 'Application' branch should be completely unsuprising to you. It follows the same patterns we've laid out in the previous sections. The 'Function' branch is a bit more complicated. We're now inserting monomorphic bindings into our type environment. Remember, this is a let-bound polymorphic language. There is no "let" preceeding the lambda's argument. It is not polymorphic. Though I'm focusing on the syntax of the keyword "let" there are deeper reasons to restrain polymorphism to Let expressions only. Not least of which is soundness (at least within this algorithm).

Looking at the function expression's branch, there's something called an 'inner mono set' which extends the outer monoset with the free variables of the function's parameter type. The inner mono set's raison d'etre is relatively straight-forward to explain. Whatever types were monomorphic before the function's body stay monomorphic within the function's body. Its lexical scoping rules but for your type system.

If I were a really cool guy, I'd have used a persistent HAMT and I wouldn't need the clone but, then again, we wouldn't have a reason to talk about this subtlety.

Before we go let's talk about 'free variables'. Consider this function:

fun x -> x

What is the type of x? No clue. There's not enough context. The variable is context... free! You've cracked the code. That's it. There's really nothing more to say about it.

There is an additional type of type variable which is closely related to free variables: the quantified type variable. Consider this expression:

let y = fun x -> x in ...

What is x's type? Still no clue. x is still free inside its own function body but x is no longer a free variable once it enters the in expression. It becomes 'quantified' at that stage.

If you've heard of "forall" this is exactly what this is. The best way to understand forall is as a function for generating types. Since 'y' is polymorphic, usage of y can vary by callsite. y's type therefore is ∀x. x -> x. Using basic alegbraic reasoning, if we substitute TBool or TNum for x what is the output of the type generating function? TBool -> TBool and TNum -> TNum. This is known as instantiation.

To tie it all together, free variables are generalized into quantified variables before being instantiated into monomorphic types.

Enough talk. Let's write some code that generates free type variables.

impl Type {
    fn free_vars(&self) -> HashSet {
        match self {
            Type::TArrow(parameter, body) => {
                let mut free = HashSet::new();
                free.extend(parameter.free_vars());
                free.extend(body.free_vars());
                free
            }
            Type::TVariable(v) => HashSet::from([*v]),
            _ => HashSet::new(),
        }
    }
}

This is all we need to find the free variables of a type. For the quantified variables we'll need to extend this greatly. It involves adding methods that are never called in the constraint generation phase. We'll add them now because we're on the subject and it will let you see exactly what's relevant to constraint solving and what's relevant to generation.

impl Type {
    fn free_vars(&self) -> HashSet {
        match self {
            Type::TArrow(parameter, body) => {
                let mut free = HashSet::new();
                free.extend(parameter.free_vars());
                free.extend(body.free_vars());
                free
            }
            Type::TForall(ty, quantified) => {
                let mut free = ty.free_vars();
                for q in quantified.iter() {
                    free.remove(q);
                }
                free
            }
            Type::TVariable(v) => HashSet::from([*v]),
            _ => HashSet::new(),
        }
    }

    fn generalize(&self, monomorphic: &HashSet) -> Type {
        let quantified = self
            .free_vars()
            .difference(monomorphic)
            .cloned()
            .collect::>();
        Type::TForall(Box::new(self.clone()), quantified)
    }

    fn instantiate(&self, tygen: &mut TypeGen) -> Type {
        fn find_and_replace(t: Type, subst: &HashMap) -> Type {
            match t {
                Type::TArrow(parameter, body) => Type::TArrow(
                    Box::new(find_and_replace(*parameter, subst)),
                    Box::new(find_and_replace(*body, subst)),
                ),
                Type::TVariable(i) => subst.get(&i).map_or(t, |v| v.clone()),
                _ => t,
            }
        }

        match self {
            Type::TForall(ty, quantified) => {
                let subst = HashMap::from_iter(quantified.iter().map(|v| (*v, tygen.fresh())));
                find_and_replace(*ty.clone(), &subst)
            }
            _ => self.clone(),
        }
    }
}

First the free_vars addition. We now consider a TForall type. It's free variables are simply whatever the free variables of its principal type are minus whatever is quantified within the type scheme. Until we write our solver this doesn't carry much weight, but we can take it at face value that we're performing some set difference operation where the only things that are free are the things that have not already been spoken for by the wrapping TForall type.

Generalization is realtively easy to understand as well. We get the free variables of the type and then subtract the 'mono set' given to us. The final output is a TForall where its principal type is the type being generalized and its quantified variables are whatever has not declared monomorphic in the outerscope.

For example:

fun x -> let y = fun z -> z in ...

y produces the TForall type. x is monomorphic and already exists in the monoset our constraint generation function produced. It can not be quantified. It must remain free. It will be the type variable that is removed from the computed free variables set. z will be the other computed free variable. It remains in the set (and is therefore a quantified type variable) because it is polymorphic.

If this isn't clear, refer to the earlier paragraphs where I discuss this "function body scoping" property of the algorithm.

Instantitation, you'll recall, is the process of taking a polymorphic type and producing a monomorphic type. That's precisely what we're doing here. For each quantified type variable, we produce a new, monomorphic type variable. We then reconstruct the type except replacing its quantified type variables with the new free type variables. This makes the resulting type more monomorphic than the previous type but does not guarantee fully monomorphism. There could be nested polymorphism still within the type. Crucially, whatever becomes monomorphic during this operation stays monomorphic.

Take a bow. You're officially done generating constraints. Technically you were done a while ago but we sprinted ahead because we had a good opportunity to identify ownership in this generalizing-instantiating soup. I wonder if it gets any easier from here...

An Advanced Constraint Solver

The solver has been neglected for a while. Truth be told, I couldn't think of a good intermediate step that was simple enough to educate, and correct enough to pass some primitive test coverage. Unfortunately, we get to 'draw the rest of the fucking owl'.

Here's the plan, we've got a sack of constraints. We're going to pull out a constraint, see if its solvable, and, if it is, solve it. If its not solvable it goes back into the bag until we run out of other constraints to solve. Then we'll try it again. If it still fails we panic, but if it succeeds the program is correct.
