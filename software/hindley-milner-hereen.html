Hereen's Implementation

Preamble

Before we can infer the types of an abstract syntax tree we need to define one. We need two types. First we need some recursive representation of an expression hierarchy. Second we need some way of defining types. I've chosen an enum representation. You can choose what you prefer.

enum Expr {
    Number(i64),
    Add(Box, Box)
}

enum Type {
    TNumber
}

Constraint Generation

Constraints are equations which operate on types. This sounds complicated but equals is the only operator. Generating a constraint implies "this type is equal to that type". The job of a constraint generation algorithm is to recursively walk an AST and assert "T1 == T2". If the two types are not equal the expression does not "unify" and a type error is returned.

Let's define a type signature for our constraint generation function to get started.

fn generate_constraints(expr: &Expr) -> (Type, Vec<(Type, Type)>)

We take an expression and we return a type and a vector of type doubles (the constraints). The type we return is the prinicipal type of the expression. The constraints we return constrain that principal type. The principal type is also known as the expression's "most general" type.

Okay let's generate constraints for our Number expression:

match expr {
    Expr::Number(_) => (Type::TNumber, vec![])
}

The return type of the Number expression is TNumber and it generates no constraints. We hard code literals to their type. There's nothing to infer. There are no constraints to solve. A number's most general type is just a number.

TNumber is a type but its a certain kind of type. Its a monomorphic type. Mono meaning its only one thing. Its not a number and a string. Its just a number. We'll see polymorphic types later but for now just know that we are only operating on monomorphic types and that makes the algorithm much easier.

Next, we'll generate constraints for the addition expression. This is another hard coded type but it will demonstrate the constraint generation process.

Expr::Add(left, right) => {
    let (t1, mut cs1) = generate_constraints(left);
    let (t2, mut cs2) = generate_constraints(right);
    
    let mut constraints: Vec<(Type, Type)> = vec![];
    constraints.append(&mut cs1);
    constraints.append(&mut cs2);
    constraints.push((t1, Type::TNumber));
    constraints.push((t2, Type::TNumber));

    (Type::TNumber, constraints)
}

Expressions are trees. We need to choose which branch to evaluate first. We picked left but we could have picked right.

After evaluating both branches we combine the constraints from both into a single vector and generate a couple more constraints. The addition expression requires its arguments are number types. It pushes that constraint into the list of constraints generated for this function. If you passed a string as the first argument the constraint solver should tell you that a string can not be used in the addition expression.

Finally we return the constraints and hard code the fact that addition always returns a number. Not every function can be hard coded but this one can be.

Solving Constraints

A constraint solver is even easier than a constraint generator (at least for now). We iterate over the constraints and check that they match. If they don't then we raise an error. What could be simpler?

for (c1, c2) in constraints {
    if c1 != c2 {
        panic!("How could you have possibly messed this up?")
    }
}

If Expressions

If expressions contain three subexpressions. The "condition" expression, the "then" expression, and the "else" expression. Alternatively referred to as "consequence" and "alternative".

If(Box<Expr>, Box<Expr>, Box<Expr>)

The if expression has two rules in our language. First, "then" and "else" expressions must have the same type. Second, the "condition" expression must be a boolean type.

Let's add a new boolean type to our Type enumeration.

enum Type {
    TNumber,
    TBoolean
}

Next we generate constraints for each of the three subexpressions, merge their constraints, apply some of our own constraints, and return a type.

Expr::If((cond, then, els_)) => {
    let t = tygen.fresh();

    let (tcond, mut c1) = generate_constraints(cond);
    let (tthen, mut c2) = generate_constraints(then);
    let (telse, mut c3) = generate_constraints(els_);

    let mut constraints: Vec<(Type, Type)> = vec![];
    constraints.append(&mut c1);
    constraints.append(&mut c2);
    constraints.append(&mut c3);

    constraints.push((Type::TBoolean, tcond));
    constraints.push((t.clone(), tthen));
    constraints.push((t.clone(), telse));

    (t, constraints)
}

The process of generating constraints for if expressions mostly mirrors addition. Where it differs is in the generation of a fresh type variable. Fresh type variables are meaningless placeholders. They do nothing except occupy space until its time until unification.

The reason we use a fresh type variable, rather than asserting the "then" and "else" conditions equal each other explicitly, is so we can find the most general type of the expression. Presently this distinction in our program has no value but it will have some value later.

Let's update our implementation to support fresh type variable generation.

fn generate_constraints(expr: &Expr, tygen: &mut TypeGen) -> (Type, Vec<(Type, Type)>)

Add a new Type member "TVariable":

enum Type {
    TNumber,
    TBoolean,
    TVariable(usize)
}

And add a new type "TypeGen":

struct TypeGen(usize);

impl TypeGen {
    fn new() -> Self {
        TypeGen(0)
    }

    fn fresh(&mut self) -> Type {
        self.0 += 1;
        Type::TVariable(self.0)
    }
}
