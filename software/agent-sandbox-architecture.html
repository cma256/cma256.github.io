An Architecture for AI Agent Sandboxes

Published on Monday, August 3, 2026

In this article I will describe the architecture I chose for an AI Agent Sandbox project but not its alternatives (of which there are many). I will also not describes the exact reasons which funneled Sentry's attention in this direction. Some of those reasons are good, bad, or stale. This was an eight month long project of which my participation covers only the final three week period.

Context

At Sentry one of our business objectives is to enable "self-healing" software. "Self-healing" software describes an agentic loop where a telemetry collector (Sentry) analyzes signals emitted from customer software and automatically emits new software to repair or enhance the customer's software without the customer's input. One requirement of this push is that we are able to execute arbitrary custom software within a sandboxed environment. This might mean an AI agent can run a Python script or a bash command or build the customer's project and run the test suite.

The Agent Sandbox project was a long-running project meant to satisfy these requirements. It consisted of three distinct pieces of software. A client, a router, and a runtime. The router acted as a proxy; bridging the client and the sandbox. The router also behaved as an orchestrator provisioning runtimes for client's to execute AI agent commands on. The router was a FastAPI HTTP service. The runtime likewise was also a FastAPI HTTP service. The router exposed an HTTP interface for the client. The runtime exposed an HTTP interface for the router. The client implemented a simple HTTP GET/POST scheme.

The project had been abandoned (by attrition) a week before I was assigned to the project. I was brought in, as the sole project maintainer, to extend the feature-set of the unreleased Agent Sandbox Platform but discovered that the Agent Sandbox, as it existed, was not production ready. The system was fantastic in many regards. The infrastructure and security model were well thought out. And the core client-router-runtime architecture was, in my opinion, the correct approach. However, the implementation of the router was a sore spot. In short, it was not durable, not fault-tolerant, suffered from at least one security issue, and had two unbounded memory growth issues. After reporting these defects I set out to fix the project as quickly as was possible and responsible. There was at least one feature which was blocked by the Agent Sandbox's deployment timeline. That acted as a significant tailwind to push the design and implementation process forward as quickly as possible.

Designing a New System

The Agent Sandbox implementation was singularly focused on one use case. For example, provisioning a runtime required a git repository because it was assumed cloning a git repository would be the immediate next step for all use cases. The core issue with the design was a lack of generality. This lack of generality contributed to nearly all of the production-readiness issues.

Recognizing that the router took on too much responsibility and too much state, I began my design process by moving as much responsibility as possible to the client and moving as much state as possible to the runtime. This would eventually leave me with an entirely stateless router and a fault-tolerant client which was firmly in control of its runtime. The runtime, decoupled from its original use case, became a dumb program execution engine.

The Process and Pipe Model

UNIX famously popularized the process and pipe execution model (or so I think). You spawn a process and get three file descriptors in return (referred to as fd for the remainder of this article). The three fds are STDIN, STDOUT, and STDERR. If you want to communicate with a program you write to the STDIN fd. If you want a program to communicate with you, you read from that program's STDOUT and STDERR fds. The fds are byte buffers. You read from them like you would any other stream. Specifically a network stream.

Once we consider that the three fds UNIX offers us are the same primitive as the two buffers a TCP connection gives you (SO_RECVBUFF and SO_SNDBUFF) then you can start imagining a world where you connect the two together. Receive something from the network? Pump STDIN. Did STDOUT or STDERR stir? Pump SO_SNDBUFF.

What's both interesting and unsuprising about this system is how well-behaved it is (almost as if the platform was designed to work this way). The TCP in and out buffers and the process's STDIN/OUT/ERR buffers are all capable of signaling back-pressure to one another. If you produce to a STDIN buffer but the process is not capable of consuming input the Kernel will accept and buffer input only up to a point. It will eventually signal that it is blocked and not accepting data until the process consumes it. If you're clever you can use these signals and decide to not block your system and instead yield to its executor so another process, or another machine, can consume the machine's limited resources.

This (combined with some future, to-be-discussed innovations) produces a remarkably memory-stable system. If you're able to signal back-pressure a non-responding process at one end and a 100GiB file on disk at the other end consume nearly no memory at all. Bytes are produced and consumed in a just-in-time manner.

Designing a Protocol

So far I've expressed my admiration for UNIX (Linux specifically) for doing so much of the work for us. But the system needs to be more than memory-efficient. It needs to, potentially, accept commands in between other commands. For example, if our client is pumping a 100GiB file to the runtime and the client's orchestrator decides its time for the client to shutdown, we'd like to signal the runtime that the client is shutting down without waiting for that 100GiB file to stream to the other end. This gives the runtime the ability to clean up or commit whatever it needs to for when the client resumes.

Remembering the router's role from earlier, we'd also like the client to communicate with the router certain orchestration signals while, potentially, simultaneously sending a 100GiB file to the runtime.

Finally, we want to consider STDOUT and STDERR. These buffers may be produced to in parallel by our spawned process. Sending bytes from STDOUT and STDERR over the wire at the same time would lead to a corrupted stream as the two unrelated byte streams are interleaved. An easy fix is to fully drain STDOUT and STDERR to the runtime's memory and then send each sequentially over the TCP socket back to the client. This is a slow and memory-intensive process and output is only received after the process completes. This makes it non-viable for any system which values real-time communication or has constrained memory resources (as our machines will).

To solve these problems I turned to a custom "framed" protocol. A framed protocol chunks a stream and wraps it with control bytes. A leading u8 byte acts as the type byte, the next four bytes are a u32 representing the length of the remaining data in the frame. Framing messages enables arbitrary interleaving between frames of differing types. As you receive frames you route the frames to the buffer matching the type. In Python's syntax control header parsing looks like this:

    Struct("!BI").unpack(stream.readexactly(5))

A u32 payload length was chosen because the maximum frame size was restricted to 1MiB. Payloads over 1MiB span multiple frames. An empty frame signals EOF. 1MiB was chosen as the payload size because it amortizes the cost of the header parsing without being a DOS risk. It is also a power of two which should be friendly to our system's memory allocators preventing us from fragmenting as much memory when a stream is full. Though, I never tested this to prove it actually did anything, it is a kind gesture which I'm fairly sure is helpful.

There are other features of the protocol in regards to Kubernetes orchestration, protocol version negotiation, session signalling, and keepalive which I will not describe. But, rest assured, its there and solves for its use case. The final thing I'll say about the protocol is that it is general. The commands you issue are totally uncoupled to any particular use case. You issue commands to the runtime and recive exit codes and streaming output. There is nothing in between you and the machine. To your agent harness it appears as though it is running on that machine.

Authentication

A brief aside about authentication. This is a fully internal system and does not require protection from the outside world. Even so I wanted to ensure that Sentry engineers could not violate a trust boundary and accidentally access customer sensitive information. The solution is simple. Each client generates a 128-bit token. The token is never stored and only exists in the client's memory. The token is sent to the router with each new connection. The router is a stateless service and so can not know if this token is valid or who it refers to or what access it provides. The router accepts the token, computes the SHA256 hash of the token, truncates it slightly for Kubernetes reasons, and uses this truncated hash as the runtime pod identifier. When the router looks up the pod ID in etcd it knows that if the ID maps to a valid pod then the client must own it and therefore is authenticated to access it. Pod IDs are semi-accessible and so possession of the pod ID is not sufficient to communicate ownership.

This is somewhat atypical for the web domain. Its more common to store tokens in a database and then have that token maintain relationships to the data it owns. For this project, given my timeline, I did not have time to provision additional infrastructure to support such a scheme. Nor was it particularly desirable. Additional infrastructure is an additional maintenance burden. Both operationally and code-wise. Re-using etcd as our source of truth maps exactly to our use case of use etcd as our source of truth. The system can never exceed the feature set Kubernetes offers and so Kubernetes is the ideal target.

The ephemeral nature of the token means we can not resume a session after a client restart. There was a planned addition to support this. The token would have eventually been stored somewhere and retrieved by the client at time of need. Here we would have used a relational database and asserted that the client had the correct access rights before handing over the token.

Implementation

I will spend very little time on implementation. You can accomplish a proof of concept with a fully functioning client, router, and runtime in roughly 200 lines of code. The production implementation was fully 2000 lines of code. All of these additions are full protocol adherence, resource clean-up, and code comments. If you significantly relax your attitude toward these items then you too can have this system in about an hour's typing time.

Below I've shared some pseudo code to communicate how the runtime works in practice.

    async def connection_handler(reader, writer):
        async def conn_writer(stream: StreamReader, write_chan: Callable[[StreamWriter, bytes], None]):
            while True:
                data = await stream.read(4096)
                if not data:
                    return None
    
                write_chan(writer, data)
                await writer.drain()

        async def conn_reader() -> None:
            while True:
                process.stdin.write(await read_frame(reader))
                await process.stdin.drain()

        process = await asyncio.create_subprocess_exec(
            "/bin/bash",
            "-c",
            command,
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            start_new_session=True,
        )

        task_stdout = asyncio.create_task(conn_writer(process.stdout, write_stdout_frame))
        task_stderr = asyncio.create_task(conn_writer(process.stderr, write_stderr_frame))
        task_client = asyncio.create_task(conn_reader())

        task_process_exec = asyncio.create_task(process.wait())
        done, _ = await asyncio.wait((task_process_exec, task_client), return_when=asyncio.FIRST_COMPLETED)

        if task_process_exec in done:
            await asyncio.gather(task_stdout, task_stderr, return_exceptions=True)
        else:
            task_process_exec.cancel()
            raise task_client.exception()

        await asyncio.gather(task_stdout, task_stderr, task_client, return_exceptions=True)


    async def main():
        server = await asyncio.start_server(connection_handler, HOST, PORT)
        async with server.serve_forever():
            await server.wait_closed()


    if __name__ == "__main__":
        asyncio.run(main())

And here's a simplified view of the router's core loop. The core idea is expressed as: connect to the sandbox and blindly relay bytes from A to B and B to A. This blind relay means we never have to inspect the payload and so incur very little performance penalty from any Python code. We're entirely network bound.

    async def session_handler(reader, writer, message):
        sandbox_id = _sandbox_id(message["token"])
        server_reader, server_writer = await connect_to_sandbox(sandbox_id)

        keepalive(writer)
        keepalive(server_writer)

        try:
            write_control_frame(server_writer, message)
            await server_writer.drain()
        except Exception:
            server_writer.close()
            try:
                await server_writer.wait_closed()
            except OSError:
                pass
            raise

        await asyncio.gather(
            relay(reader, server_writer),
            relay(server_reader, writer),
            return_exceptions=True,
        )

This code is not real or useful as code. I've significantly cut down a lot of the protocol and error handling components. What's intended with the code is to communicate the type of system we're working in. Its a TCP server which accepts long running connections. Process lifetime and connection lifetime are tied though its not well communicated in the code above. There were plans to disentangle those two lifetimes in the case of connection partition or router shutdown. Due to time constraints this was not implemented.

The runtime spans 40-ish lines and the proxy another 20. A functioning version might take another 80 but I'm not sure. This is the core engine of the system. A runtime connection spawns a process which consumes from and writes to the connection's TCP buffers. A client connection demands a sandbox connection and the router brokers the network relay.

The system is multiplayer allowing multiple clients to execute commands on the same runtime at the same time. We can see the Kernel buffers being drained 4KiB at a time keeping our memory foot-print small. No EOF handling in the sample code's connection reader but it existed in the full implementation.

Its a shame how much I've had to cut. I would show you more but this system was never open-source and I do not intend to ask permission to share it.

Success

We have a fully general system capable of multiplexing multiple signals over a single connection. The system provides full access to the runtime and enables as complex (or not) client behavior as is required for its use case.

The system was benchmarked and achieved a maximum throughput of 6.8 gigabits per second. It was also memory stable as advertised (/dev/urandom output transfer from the client to the runtime's /dev/null). Actual production behavior would vary but that would be entirely dependent on how the runtime was used and not the system I designed.

The programs themselves are dependency free. There are no third-party dependencies required to make this work. This is purely the asyncio module, subprocess module, and some other anciallary data munging libraries from Python stdlib.

In the final implementation clients would have been able to specify the runtime's image, CPU and memory request, network egress privileges, and connection lifecycle. However, the project did not last that long, and, as of writing, is currently being re-orged to another department. What that team will do with the project I do not know. Hopefully they find this software as useful and interesting as I do.
