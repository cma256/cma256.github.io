To Proxy or to RPC

Published on Thursday, August 27, 2026

In my work on the unified source code management platform, I added an HTTP proxy interface which stills bears the incorrect (but backwards-compatible) label of "rpc". Now, some months later, I've been day-dreaming about a potential feature addition to the SCM platform -- a true RPC system.

This naturally begs the question: why? Why do you need it? When is one preferred over the other? Can the proposed RPC system replace the proxy system? If you could go back in time would you have started with an RPC and never developed the proxy? Are these two even in the same domain of problems?

I've been thinking about these questions myself and I came up with an analogy that may be more fun than informative but, none the less, I really like.

I think of the two as the difference between a compiler and a transpiler. To radically over simplify, a compiler takes the user's code and converts it into a set of instructions a machine can execute. A transpiler takes the user's code and transforms it into another form. You execute a compiler's output. You compile a transpiler's output first and then execute.

I don't want to get into a PL theory argument about what the limit of transpilation actually is. This is, at least, the popular conception of what transpilation is. If you like the analogy then roll with it and if you don't then ignore it.

As it relates the the SCM platform, the difference between an RPC call and a proxy call is exposed in how you roll out changes. With the platform's proxy interface you can run an alpha version of the proxy server while the proxy client runs version two or two-hundred or two-hundred million. Every version of the platform compiles down to the same HTTP primitives: headers, paths, query params, body data, etc. There is nothing that changes version to version. So a proxy server and a proxy client can be wildly desynced version-wise.

Backwards compatibility requirements are totally local. If you upgrade your client to version twelve, it may have a breaking change which you need to contend with. But because the server does not push a requirement onto clients to upgrade, legacy clients can run forever. There is no such thing as a "deprecation notice".

In an RPC system this is not true. Backwards-compatible changes are possible -- you can strengthen a promise or relax a constraint -- but you can't make arbitrary changes. And you certainly can't turn your brain off and code. In the early days of the SCM platform, there was only one client. Backwards-compatibility concerns, from a client perspective, were non-existent. Changing an interface meant you were the sole consumer of that interface. If we used an RPC system in such a scenario, a rollout of a new version of the SCM-platform would have required a backwards-compatiable release, a migration of the server, and then a migration of the client. This is not conducive to fast iteration.

Conversely, the proxy allows you to release whatever you want. If the release is not backwards-compatible then you get a slew of compiler errors that you need to work through. But that's it. The brain is totally off. There is no need to consider a live migration of production usage. There's no need to consider production traffic at all. Whatever was running will continue to run.

Going back to the compiler metaphor, because we have a stable "instruction set" the fact that the "compiler" changed is immaterial to the "machine's" ability to execute the "binary". They're two distinct systems. The SCM platform is the compiler and the proxy is the machine. The proxy is never touched (because it never needs to be) so it always knows how to execute the output of the platform "compiler" even if that "compiler" has been radically transformed.

This comes at a cost. The "compiled" output is not trivially readable. With an RPC system you're not given a set of instructions to execute. You're given a request: "please call this function with these arguments". This is a higher level request that communicates intent.

Create a pull request with this title please.

Rather than...

Proxy this HTTP request. Now!

An RPC system allows you to more easily say "you're not allowed to do that". This is especially useful if you want to do something crazy like expose the platform over HTTP to any authenticated user, making the platform driveable from a JavaScript application in the browser, removing dozens, or even hundreds, of bespoke SCM implementations on the backend.

But, of course, nothing is free. The RPC system immediately implies the client and server are tied. They have a similar understanding of the shape of a function and similar expectations of output. You must think about migrations and backwards-compatibility. And this mindset permeates your work even if your side of the world only interacts with the proxy. The fact that the RPC system exists at all means you must contend with it.

The question I asked earlier "would you implement an RPC system from the start rather than a proxy" has so far been unanswered. I hope you have developed your own opinions. As for mine, I would not change a thing. We did not need an RPC system so I did not build one. We avoided the costs of one for months. An incredible amount of adoption, iteration, and progress was achieved over those early months. More than a dozen engineers contributed and I scarecly interacted with them. I didn't need to brow beat about backwards-compatibility. None of the engineers had to consider live migrations. There was never a production incident where a version mismatch broke some use case. There was never a production incident at all.

It was truly a wonderful project. Productive, stable, stress-free, decentralized. I would go so far as to say uncoordinated but I'm afraid that might communicate the wrong connotation.
