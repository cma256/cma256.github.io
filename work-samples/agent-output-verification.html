Agent Output Verification

Published on Sunday, August 16, 2026

Situation Description

The Seer coding agent downloads a customer's repository, modifies it, and pushes those changes to GitHub. The coding agent does not verify its output through static or runtime analysis. It sometimes verifies its output with the LLM-as-a-judge strategy. The agent runs in a different pod from the customer's repository contents. Agent commands are proxied to the agent sandbox. Problem Diagnosis

No Output Verification

  1. Static verification. The agent does not verify its output passes the customer's linter, formatter, type-checker, or other static analysis tooling requirements prior to submitting the change to the customer.
  2. Runtime verification. The agent does not verify its output can compile, run, or pass the test suite before submitting the change to the customer.
  3. AI verification. The agent's output is not judged by another, independent LLM to verify the output's quality prior to submission.
  4. CI verification. The agent does not verify its output passes in the customer's CI. If the pull request fails any of the customer's status checks the agent does not resume, consume the CI runner's output, apply changes from the feedback, and push to the new change set to the customer.

Functional but Unacceptable Changes

An agent may produce a correct change in isolation while solving only part of the problem. A symptom may be fixed while the root cause still produces the incorrect inputs. Fixing the symptom while leaving the root cause suppresses the error while still leaving the customer vulnerable to the broken code path.

Unresolvable Ambiguity

When the agent encounters an ambiguous decision, one where the correct change depends on intent the repository cannot reveal (such as whether a bug fix should preserve or change user-visible behavior), it has no channel to ask the customer. The agent must guess. A wrong guess produces a change that is well-formed but wrong.

Customer Agent Instructions Ignored

Global AGENTS.md files are never read. Nested AGENTS.md are read only if the agent accesses a file in the directory containing the AGENTS.md file. The agent does not auto-discover, read, or use customer defined SKILLS. Without this information the agent is missing a direct encoding of the customer's intention.

Problem Delimitation

Customers expect a change proposed by Seer to carry the same confidence as a change proposed by a peer. Changes must conform to the repository's standards, they must compile, they must run, and they must pass the test suite. Seer publishes changes it has not checked against any of these. Before a customer sees a proposed change, it should have been verified against their repository's own definition of correct.

We will focus exclusively on output verification. The remaining problems are left for other projects.

Strategic Direction

Candidate Strategies

Candidate strategies are not mutually exclusive with one another.

  • Execute customer software in a sandbox - Install dependencies and run the customer's build scripts, static analysis, and test suite inside the agent environment, letting the agent iterate on failures before publishing.
    • Sub-strategies:
      • Install with detect_env.py and custom build scripts on a universal image.
      • Install with CI configuration file on a universal image.
      • Install on a minimal image with an opinionated environment manager such as the nix package manager.
      • AI-guided installation on a universal image.
        • The [REDACTED] approach.
  • Execute customer software on their machine - The customer's development machine already has a functioning build which can be used to verify our agent's output. The coding agent's commands are sent to the customer's machine and the results of the commands are sent back to Sentry.
  • Execute customer software on a shared third-party's machine - Services such as GitHub CoPilot and GitLab Duo Agent Platform re-use the customer's CI configuration to build a development environment within their infrastructure. The cost of the environment is borne by the customer. Third-party agent harnesses are allowed to execute commands within the environment.
  • Reuse the customer's CI - Publish to a draft branch and read the customer's existing CI results as the feedback signal, rather than reproducing their build ourselves.
  • Static analysis only - Run language-aware tooling (type checkers, linters) that does not require a full, working build of the customer's software.
  • LLM as a judge - Run a judging agent which takes one agent's output and verifies that the output matches its expectations and the customer's expectations based on their repository's configuration.
  • Universal Image Only - Sentry provides a universal image to the agent which can run arbitrary code for the set of pre-installed languages but does not execute the customer's software. The agent is expected to test the software it writes in isolation.
  • Do nothing - Always a valuable strategy to evaluate.

Evaluation Criteria

The evaluation criteria are every reasonable metric by which we can judge a potential solution. Not every criterion is applicable to every solution. A solution's capacity to solve for each criterion is not indicative of that solution's value. The purpose of the matrix is to document trade-offs and to act as a guide in the decision making process.

  1. Untrusted Code Execution. Installing and executing customer software means executing untrusted code. A maliciously constructed repository could be used to attack Sentry's infrastructure.
  2. Environment Satisfiability. We may not be able to construct an environment that can build the customer's software at all. The repository may lack build instructions (informal, unpublished, or proprietary internal tooling). The build ecosystem is vast and unconstrained. Build systems (make), language tooling (uv, pip), and environment managers (nix) compose into an unbounded space of build semantics. The required host may be unsupportable: a Windows machine, a specific Linux distribution, or specialized hardware (GPUs/NPUs/TPUs, large core counts, large reserved memory pool).
  3. Build Determinism & Verifiability. Even when a build is possible, its result may not be trustworthy or repeatable. Third-party package providers are unpaid, unaware of our usage, and may rate-limit, throttle, or fail under Sentry's load. Dependencies may be mutable or unavailable, producing different outputs run to run. A success in the agent environment may not translate to CI or production. The build may produce an artifact that isn't representative of what the customer expects, and is incapable of running their static analysis, compiler, or test suite.
  4. Resource Economics. Customer builds may consume significant compute or idle on slow networks while bootstrapping. Unsatisfiable environments, non-reproducible builds, and unusable artifacts all consume resources without providing value.
  5. Feedback Loop Latency. A common agent pattern is to utilize the write, run, observe, revise loop. A strategy's value depends on how fast and how often the agent can verify its work and if it can verify it within a single session.
  6. Output Quality. How much does the strategy actually improve the changes customers receive?
  7. Required Level of User Effort. How much configuration, onboarding, or ongoing participation does the strategy demand from the customer before it delivers value?
  8. Customer Coverage. What fraction of customer repositories can the strategy serve? Language ecosystems, build tooling, and other requirements all narrow the set of repositories a given approach can handle.
  9. Customer Familiarity. Does the strategy behave in ways customers already understand and trust?
  10. Graceful Degradation. Builds are, potentially, a non-deterministic process. Failures and partial failures are expected. Given a particular approach how capable is this approach of retaining capabilities in the presence of faults.
  11. Setup Cost and Cache-ability. How expensive is the initial environment construction, and can that work be amortized across sessions?
  12. Work Requirements and Maintenance Cost. How much engineering effort does the strategy require from Sentry to build, and what is the ongoing burden of keeping it working? Approaches that track a vast, evolving ecosystem (build tools, language versions, package registries) carry a permanent maintenance tax, while narrower approaches may be cheaper to sustain but deliver less.
  13. Agent Network Requirement. Does this strategy require an LLM to have network access?
