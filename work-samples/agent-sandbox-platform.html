Connection Pools are not Connection Limits

Published on Wednesday, August 20, 2025

Situation Description

While performing a security audit of the sandbox-router repository several substantial defects were observed. These defects are serious enough to stop the release of the sandbox-router to the DE and US environments and should have prevented a release to the S4S2 environment. Until these defects are resolved the sandbox-router and sandbox-runtime can not be released.

Problem Diagnosis

In short, the system is not fault-tolerant, durable, performant, correct, stable, secure, or cost-efficient. It can not survive redeploys. It does not appropriately manage its timeouts.

Minor deficiencies have been omitted in the interest of time. Additionally, there may be significant deficiencies which I have not yet discovered. Given the complexity of the system I expect it will take some time to fully discover its defects. This list will be continually updated as new problems are discovered.

Process Local Task State

“Coding Tasks” are stored in-memory within a sandbox-router server and are not replicated to the other sandbox-router servers. Requests to GET /coding-tasks/{id} will 404 unless the load balancer is smart enough (or lucky enough) to route the request to the correct server (not configured). The sandbox-router is currently deployed to S4S2 with the replica count set to 2.

Process Local Credential State

Git tokens are stored in memory within the credential-proxy. A credential-proxy restart will invalidate every sandbox's API key. The credential-proxy is written under the assumption it is single-server, never crashes, and never redeploys. If multiple credential-proxy servers are active the sandbox may experience 4XX errors even though its credential is correct.

Unbounded Sandbox Router Memory Usage

Tasks are never evicted from the in-memory _tasks dictionary. If the sandbox-router lives long enough it will eventually consume all of its allocated memory.

Tasks Are Not Durable

Tasks are stored in-memory. Failure or redeployment of a sandbox-router node will incur data loss.

Tasks Are Not Idempotent

A coding-task may be scheduled but never return a response to the client. The client is unable to idempotently retry the task or otherwise resume the connection. Idempotency is particularly important because task commands can mutate the state of the sandbox. Duplicate commands can leave the sandbox in an undefined state.

Tasks Can Not Be Resumed

On sandbox-router failure or re-deployment, the sandbox server is still active and processing the client's request. The client has no capability of re-establishing its connection to the sandbox. The sandbox and sandbox-router have no mechanism for negotiating session recovery.

Task Cleanup is Best-Effort

Cleanup failures are swallowed and never retried. Failure to retry exceptions could orphan resources.

Incomplete Task Cleanup During Redeploy

When redeploying the sandbox-router service there is no guarantee the cleanup procedure will actually execute to completion. Failure to do so could orphan resources.

Blocking Operations in the Sandbox Router Event Loop

Synchronous I/O operations are being emitted without awaiting them in an async task. This blocks the single-threaded event-loop making the FastAPI HTTP server single-threaded and blocking.

Sandbox TTL Can Expire Mid-Task

The sandbox router defines a setup TTL of 600 seconds and an agent TTL of 660 seconds. However, the sandbox TTL is hard-coded as a maximum of 900 seconds. The deadlines for these two contracts are incongruent.

Credential Proxy Potential Credential Leak

Credentials are stored in an in-memory credential registry within the credential-proxy service. Additions and removals to the registry are performed by the sandbox-router service. If the sandbox-router crashes or redeploys while it has a credential in the registry, the sandbox-router will not remove that credential from the proxy leaving it orphaned for the life of the credential-proxy.

These credentials could potentially be leaked though no known mechanism exists. This also represents a potential memory-leak, though, the volume is so slow and the mechanism so rare that we'd never see on in practice.

Infinite Poll on Task Scheduling Failure

When a coding task request is received we store a CodingTaskResult instance with a status of pending. If the asyncio task fails, or otherwise never updates the task, then the client will poll the coding-task endpoint forever. There is no task execution deadline or callback that handles cancellation or failure. As previously documented, tasks are never evicted. Client's poll forever.

Kubernetes Responses Are Not Validated

Kubernetes responses are never read to determine if the request succeeded or failed.

Excessively Long Lived HTTP Requests

Multiple HTTP requests are held open for >10 minutes. There are no heartbeats or network recovery mechanisms implemented.

Task Cancellation Race Conditions

A request to DELETE /coding-task may report success without actually cleaning up the coding-task resources. There are distributed and local failure modes.

Problem Delimitation

Among this list, there are few problems which can be avoided. We might sacrifice some clean-up correctness for a coarser sandbox termination cleanup procedure, for example.

Strategic Direction

The sandbox-router assumes too much responsibility and can not possibly accommodate all of the roles it has taken on. It assumes ownership of resources it should not and does not appropriately guard those resources.

We have three options:

  1. Let the thing limp its way into production and accept the failures as the cost of operation.
  2. Fix the service. Adopt its CRUD-style architecture. Add durable stores and message queues to facilitate its mode of operation.
  3. Re-architect the service. Accept that the design is too resource intensive and flawed to deploy to production. Adopt an alternative approach more suited to the problem space.

Candidate Strategies

  1. Run the existing sandbox-router service as a single server. Merge the credential-proxy into the sandbox-router service.

    1. Solves some of the serious distributed system questions.
    2. Does not resolve many of the other performance, safety, stability, scalability, etc. problems.

  2. Fix the sandbox-router service. Add durability with Postgres or Redis. Add retry and resume semantics. Add a durable task queue such as RabbitMQ. Merge the credential-proxy into the sandbox-router service. Add semi-durable credential storage (Redis would be sufficient).

    1. A non-trivial amount of effort and resources to allocate.
    2. Design seems fundamentally broken and any fix will have to grind against the impedance mismatch between the architecture chosen and the problem being solved-for.
    3. I have serious concerns that this is the most time-consuming option and that it will not produce a worthwhile output.

  3. Re-architect the sandbox-router to be a streaming TCP proxy to a sandbox process. Move the state from the router to the sandbox. Create a binary protocol which exposes recovery mechanisms. Delete the credential-proxy.

    1. Does not require infrastructure provisioning.
    2. Requires client changes in Seer.
    3. Requires a novel protocol.

Design

Summary

  • Status: draft.
  • Release target: On or before 2026-08-28

The goal of this design is to provision sandboxes and broker connections between clients and sandboxes in a performant, scalable, secure, and general way. Generality is a stated goal of the design because it restricts the amount of features needed to implement a functioning system and allows us to rely on the platform (Linux) to do most of the work for us.

Goals

  1. Broker connections between clients and sandboxes.
  2. Enable client managed sandbox properties and lifecycle.
  3. Enable secure AI agent access to private customer source code.
  4. Enable credentialed access to remote resources without exposing credentials to AI agents.

High Level Architecture

A stateless proxy brokers requests between a client and Kubernetes and a client and a sandbox. The proxy is capable of creating, updating, and destroying sandbox runtime instances. The proxy is capable of routing bash commands from the client to the sandbox runtime. The proxy exposes the full feature-set of the UNIX process and pipe model wrapped in a framed wire-protocol for performance and correctness reasons. The protocol has a binary format and no defined output structure for stdout/err buffers. The client is expected to interpret the output of the commands it produces to the sandbox.

Technical Details

Protocol

The protocol has three components. The first is a single u8 value at the start of the frame. This is the frame type byte. The second is a 4-byte length delimiter which describes the length of the third component. The third component is an arbitrary byte sequence understood by its target.

The bytes are packed in big endian format:

{type}{length}{bytes...}
[0x01] [0x00 0x00 0x0c 0xba] [...]

Frames

The are four frame types:

  1. CONTROL
  2. DATA
  3. STDOUT
  4. STDERR

STDOUT and STDERR are egress only from the sandbox runtime. They carry stdout/err buffer data to the client. CONTROL frames are ingress only and carry Kubernetes instructions to the proxy for it to execute. DATA frames are multi-purpose. In the process and pipe model it is an ingress-only STDIN stream. In the shell model it is a bi-directional, text-based shell communication channel.

The protocol is framed for a few reasons:

  1. It bounds network usage. The client, proxy, and runtime do not need to allocate arbitrarily large buffers. They receive predictably sized buffers and can process the stream at an arbitrarily slow rate. Slow processes are able to emit backlog signals and reduce the input streams speed freeing up bandwidth for other sandboxes.
  2. It enables concurrent interleaving of multiple streams. A proxy can concurrently receive CONTROL and DATA frames. A client can concurrently receive STDOUT and STDERR frames.

Maximum frame size is 1MiB. This is large enough to amortize the cost of a frame and small enough not to be a DOS risk.

Services

There are four required services.

  1. A service to orchestrate the client (Seer and others).
  2. A service to execute bash commands (sandbox runtime).
  3. A proxy to provision and splice byte streams (sandbox proxy).
  4. A firewall to block requests according to a client-defined network policy and to transform requests according to a client-defined network policy.

The client is uninteresting in this instance. It will not be considered in this document.

Sandbox Proxy

The sandbox proxy is a stateless forwarding proxy and Kubernetes orchestration system. It accepts Kubernetes CONTROL messages and emits cluster instructions. It accepts bash command CONTROL messages and emits those to the sandbox runtime optionally pumping to the sandbox runtime’s process’s STDIN stream using DATA frames.

The sandbox proxy blindly forwards STDOUT, STDERR, and DATA frames received from the sandbox. These frames are never inspected.

The sandbox proxy is authenticated with a client generated token. The token is a random value. The sandbox proxy accepts the token and hashes it using the SHA256 algorithm. The output is the sandbox’s ID. The sandbox ID is publicly accessible and is stored in etcd. Authentication and sandbox identification are controlled from the token. Knowing a sandbox ID is not enough to access a sandbox. You must have a sandbox token. Hashing the sandbox token is a predictable one-way operation. Proxies are therefore stateless. Multiple requests may be issued to multiple proxy server’s without impacting the proxy’s ability to resolve the request.

Sandbox Runtime

The sandbox runtime spawns a process when given a command and listens on the connection for a STDIN stream (if specified by the client). As the process produces output the runtime will emit DATA, STDOUT, and STDERR frames to the proxy which will emit those frames to the client.

The client is responsible for interpreting the output. There is no protocol level parsing of these frame types. Only CONTROL frames have a specified structure.

The process spawned by a CONTROL message lives as long as the proxy connection lives. If the connection is terminated then the process will also be terminated. The connection’s lifetime is not tied to the process’s. If the pr ocess dies the connection continues on and may continue accepting input.

Sandbox runtimes are capable of accepting multiple connections. Many connections may spawn many processes which produce output to their connected clients.

Sandbox runtimes are capable of producing interactive shells. These are not useful for AI agents but are a capability of the runtime. Human users may use the interactive shell if given the ability to do so.

Sandbox runtimes persist state between commands by using the filesystem or the client’s memory. AI agents do not use persistent, interactive shells. They instead append state to their commands and carry it forward. This is a known pattern in agentic harness development.

Sandbox Firewall

The sandbox firewall is a transparent proxy. The sandbox runtime makes requests to the outside world and the firewall MITM’s those requests.

The sandbox firewall is given a network policy at sandbox create time. This policy can allow certain domains, block certain domains, and specify transformations for certain other domains. When a request is received for a domain with a transformation we terminate the TLS, alter the request according to the instruction set, encrypt the request, and forward onto its destination. To terminate TLS in the firewall the sandbox runtime will need a known certificate.
