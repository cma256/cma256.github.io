Agent Sandbox Platform

Published on Sunday, August 16, 2026

Situation Description

The Agent Sandbox Platform is a Kubernetes orchestration service and sandboxed command execution system. It consists of three distinct components: client, router, and sandbox. The router is responsible for Kubernetes orchestration (spawning and destroying sandboxes) and routing client connections to the requested sandbox.

While performing a pre-release audit of the sandbox-router repository several defects were observed. The Agent Sandbox Platform has not been released to customers in the DE and US environments. However, it has been released for internal use in the S4S2 environment.

The defects are severe enough that it should interrupt our production release schedule.

Problem Diagnosis

In short, the system is not fault-tolerant, durable, performant, correct, stable, secure, or cost-efficient. It can not survive redeploys. It does not appropriately manage its timeouts.

Process Local Task State

“Coding tasks” are stored in-memory within a sandbox-router server and are not replicated to the other sandbox-router servers. Requests to GET /coding-tasks/{id} will 404 unless the load balancer luckily routes the request to the correct server. The sandbox-router is currently deployed to S4S2 with the replica count set to 2.

Process Local Credential State

Authentication tokens are stored in memory within the credential-proxy. A credential-proxy restart will invalidate every sandbox's credentials. The credential-proxy is written under the assumption it is single-server, never crashes, and never redeploys. If multiple credential-proxy servers are active the sandbox may experience 4XX errors even though the credential was set in the proxy.

Unbounded Sandbox Router Memory Usage

"Coding tasks" are never evicted from the in-memory "_tasks" dictionary. If the sandbox-router lives long enough it will eventually consume all of its allocated memory.

Tasks Are Not Durable

"Coding tasks" are stored in-memory and are never persisted to durable media. Failure or redeployment of a sandbox-router node will incur data loss.

Tasks Are Not Idempotent

A "coding task" may be scheduled but the router may never return a response to the client. The client is unable to idempotently retry the task or otherwise resume the connection. Duplicate commands may leave the sandbox in an undefined state.

Tasks Can Not Be Resumed

On sandbox-router failure or re-deployment, the sandbox server is still active and processing the client's request. The client has no ability to re-establish its connection to the sandbox. The sandbox and sandbox-router have no mechanism for negotiating session recovery.

Task Cleanup is Best-Effort

Cleanup failures are swallowed and never retried. Failure to retry exceptions could orphan resources.

Incomplete Task Cleanup During Redeploy

When redeploying the sandbox-router service there is no guarantee the cleanup procedure will actually execute to completion. Failure to do so could orphan resources.

Blocking Operations in the Sandbox Router Event Loop

Synchronous I/O operations are being emitted without awaiting them in an async task. This blocks the single-threaded event-loop making the FastAPI HTTP server single-threaded and blocking.

Sandbox TTL Can Expire Mid-Task

The sandbox router defines a setup TTL of 600 seconds and an agent TTL of 660 seconds. However, the sandbox TTL is hard-coded as a maximum of 900 seconds. These two logical deadlines are incongruent.

Additionally, the setup and agent timeouts do not actually bound the total lifetime of the two HTTP connections. They set a maximum time to wait between bytes received. Actual connection lifetime is unbounded assuming data is flowing.

Credential Leak

Credentials are stored in an in-memory credential registry within the credential-proxy service. Additions and removals to the registry are performed by the sandbox-router service. If the sandbox-router crashes or redeploys while it has a credential in the registry, the sandbox-router will not remove that credential from the proxy leaving it orphaned for the life of the credential-proxy.

These credentials could potentially be leaked though no known mechanism exists. This is also a memory leak.

Infinite Poll on Task Scheduling Failure

When a "coding task" request is received we store a CodingTaskResult instance with a status of pending. If the asyncio task fails, or otherwise never updates the coding task, then the client will poll the /coding-task endpoint forever. There is no task execution deadline or callback that handles cancellation or failure.

As previously documented, tasks are never evicted. Clients will poll forever unless configured with their own timeouts.

Kubernetes Responses Are Not Validated

Kubernetes responses are never read to determine if the request succeeded or failed.

Excessively Long Lived HTTP Requests

Multiple HTTP requests are held open for >10 minutes. There are no heartbeats or network recovery mechanisms implemented.

Task Cancellation Race Conditions

A request to DELETE /coding-task may report success without actually cleaning up the coding-task resources. There are distributed and local failure modes.

Problem Delimitation

Among this list, there are few problems which can or should be avoided. Task resumption is not security or correctness critical. We could tolerate a coarser strategy of terminating the disconnected sandbox and starting a fresh session.

Strategic Direction

The sandbox-router assumes too much responsibility and can not possibly accommodate all of the roles it has taken on. It assumes ownership of resources it should not and does not appropriately guard those resources.

We have three options:

  1. Let the thing limp its way into production and accept the failures as the cost of operation.
  2. Fix the service. Adopt its CRUD-style architecture. Add durable stores and message queues to facilitate its mode of operation.
  3. Re-architect the service. Accept that the design is too resource intensive and flawed to deploy to production. Adopt an alternative approach more suited to the problem space.

The first option is unacceptable, in my opinion. However, it will be considered as a point of comparison.

Candidate Strategies

  1. Run the existing sandbox-router service as a single server. Merge the credential-proxy into the sandbox-router service.

    1. Solves some of the serious distributed system questions.
    2. Does not resolve many of the other performance, safety, stability, scalability, etc. problems.

  2. Fix the sandbox-router service retaining its current architecture. Add durability with Postgres or Redis. Add retry and resume semantics. Merge the credential-proxy into the sandbox-router service. Add durable credential storage with strong security and TTL guarantees.

    1. A non-trivial amount of effort and resources to allocate.
    2. Design seems fundamentally broken and any fix will have to grind against the impedance mismatch between the architecture chosen and the problem being solved-for.
    3. I have serious concerns that this is the most time-consuming option and that it will not produce a worthwhile output.

  3. Re-architect the sandbox-router to be a streaming proxy between a sandbox runtime and its client. Move the session state from the router to the sandbox. Create a binary protocol which exposes recovery mechanisms and can efficiently transport bi-directional streams of binary data. Temporarily delete the credential-proxy. Our current use case can be satisfied without it if the client has an efficient way to send customer data to the sandbox runtime.

    1. Does not require infrastructure provisioning.
    2. Requires client changes in Seer.
    3. Requires a novel protocol.

Design

Summary

  • Status: draft.
  • Release target: On or before 2026-08-28

The goal of this design is to provision sandboxes and broker connections between clients and sandboxes in a performant, scalable, secure, and general way. Generality is a stated goal of the design. We need to implement a simple system that can quickly achieve a "completed" state. Product specific requirements are omitted from this design. All extant product requirements are satisfiable from the client and do not require special modification to the router or the sandbox runtime.

Goals

  1. Broker connections between clients and sandboxes.
  2. Enable client managed sandbox properties and lifecycle.
  3. Enable secure AI agent access to private customer source code.
  4. Enable credentialed access to remote resources without exposing credentials to AI agents.

High Level Architecture

A stateless proxy brokers requests between a client and Kubernetes and a client and a sandbox. The proxy is capable of creating, updating, and destroying sandbox runtime instances. The proxy is capable of routing bash commands from the client to the sandbox runtime. The proxy exposes the full feature-set of the UNIX process and pipe model wrapped in a framed wire-protocol for performance and correctness reasons. The protocol has a binary format and no defined output structure for stdout/err buffers. The client is expected to interpret the output of the commands it produces to the sandbox.

Technical Details

Protocol

The protocol has three components. The first is a single u8 value at the start of the frame. This is the frame type byte. The second is a 4-byte length delimiter which describes the length of the third component. The third component is an arbitrary byte sequence understood by its target.

The bytes are packed in big endian format:

{type}{length}{bytes...}
[0x01] [0x00 0x00 0x0c 0xba] [...]

Frames

The are four frame types:

  1. CONTROL
  2. STDIN
  3. STDOUT
  4. STDERR

STDOUT and STDERR are egress only from the sandbox runtime. They carry sandbox process output to the client. STDIN frames are ingress only and carry data which is piped into the sandbox process's STDIN buffer. CONTROL frames are ingress only and carry Kubernetes instructions to the proxy and bash commands to the sandbox runtime. CONTROL frame instructions are JSON encoded and have a known schema.

The protocol is framed for a few reasons:

  1. It bounds network usage. The client, proxy, and runtime do not need to allocate arbitrarily large buffers. They receive predictably sized buffers and can process the stream at an arbitrarily slow rate. Slow processes are able to emit back-pressure signals and reduce the input streams speed freeing up bandwidth for other sandboxes.
  2. It enables concurrent interleaving of multiple streams. A proxy can concurrently receive CONTROL and STDIN frames from a single client. A client can concurrently receive STDOUT and STDERR frames from its sandbox.

Maximum frame size is 1MiB. This is large enough to amortize the cost of a frame and small enough not to be a DOS risk.

Services

There are three required services.

  1. A service which hosts the client (Seer and others).
  2. A service which execute bash commands (sandbox runtime).
  3. A service which provision and splice byte streams (sandbox proxy).

Sandbox Proxy

The sandbox proxy is a stateless forwarding proxy and Kubernetes orchestration system. It accepts orchestration CONTROL messages and emits Kubernetes cluster instructions. It accepts bash-command CONTROL messages and emits those to the sandbox runtime optionally pumping to the sandbox runtime's process's STDIN stream using STDIN frames.

The sandbox proxy blindly forwards STDOUT and STDERR frames received from the sandbox. These frames are never inspected by the sandbox proxy.

The sandbox proxy is authenticated with a client generated token. In the reference implementation, the token is a random 128-bit value. The exact token specification is up to the client to decide. The sandbox proxy accepts the token and hashes it using the SHA256 algorithm. The output is the sandbox's ID. The sandbox ID is publicly accessible and is stored in etcd. Authentication and sandbox identification are controlled from the token. Knowing a sandbox ID is not enough to access a sandbox. You must have a sandbox token. Hashing the sandbox token is a predictable one-way operation. Proxies are therefore stateless. Multiple requests may be issued to multiple proxy server's without impacting the proxy's ability to resolve the request.

Sandbox Runtime

The sandbox runtime runs a TCP server. On connection received, the sandbox spawns a process, executes the command received, and listens on the connection for STDIN frames. If the sandbox received STDIN frames it redirects those frames to the process's STDIN buffer. As the process produces output the runtime will emit STDOUT and STDERR frames to the proxy which, in turn, will emit those frames to the client.

The client is responsible for interpreting the output. Only CONTROL frames have a specified structure.

The process spawned by the connection lives as long as the connection does. If the connection is terminated then the process will also be terminated. If the process is terminated the client will receive the return code. It may choose to spawn a new process by emitting another CONTROL message with a bash-command, or it may close its connection.

Sandbox runtimes are capable of accepting multiple connections. Many connections may spawn many processes which produce output to their connected clients.

Sandbox runtimes persist state between commands by using the filesystem or by relying on the client's own memory.
